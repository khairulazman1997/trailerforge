## Core principles

1. **project.json is the single source of truth.** Project = folder `X.tforge/` with `project.json`, `history/`, `media/` (hash-referenced), `cache/` (regenerable), `logs/decisions.jsonl`. SQLite is index/cache/jobs only.
2. **All mutations are typed commands** (Immer patches) → undo/redo, autosave, history, events.
3. **Master storyboard + derived variants** (derivation rules + sparse overrides).
4. **Deterministic render:** `compile(project, variantId) → RenderGraph` (pure, hashable) → ffmpeg. Segmented, checkpointed, resumable.
5. **Every AI decision carries a reason object**, shown in UI and logged.
6. **Plugins** via `definePlugin({ id, apiVersion, register(ctx) })`; built-ins use the same API.
7. **Local-first:** all network calls go through a single disclosed, logged `Egress` service.

## Professional editing quality

- **Edit-grammar engine** (deterministic, explainable): cut on action, cut 1–2 frames ahead of the beat, no jump cuts, screen-direction continuity, accelerating pacing curve, holds after big moments, music edits only on bar/phrase boundaries, J/L cuts, no flash frames, no cutting mid-ease. Targets per video type come from measured reference trailers.
- **Audio:** platform LUFS targets, true peak ≤ -1 dBTP, LRA control, sidechain ducking, VO chain (HPF, de-ess, compression), 48 kHz.
- **Picture:** correct BT.709 tags/range, 10-bit internal, Lanczos scaling, judder-free fps choice, optical-flow speed ramps, per-shot exposure/white-balance match.
- **Typography/motion:** type scale, safe areas, eased animation, brand tokens, contrast checks.
- **Quality Gate** (pre-export pass/fail): loudness/peak, clipping, sync drift, black/flash frames, jump cuts, text read time, safe areas, **photosensitive flash risk**, pacing curve.
- **NLE handoff:** FCPXML / EDL / OpenTimelineIO export (M6).
- **Evaluation loop:** fixed brief corpus re-rendered on every cut-logic change, with metric regressions; human review of M4/M6 cuts.

## Effects & vector graphics

- **Vectors:** SVG templates rendered via resvg (MPL-2.0): title/tagline cards, end slates, laurels, lower-thirds, CTAs, caption boxes, icons. Brand tokens drive colors, fonts, logo.
- **Animation:** keyframe system with easing curves (position, scale, opacity, mask reveals, stroke draw-on, per-letter/per-word text).
- **Transitions:** cut, dip, flash, whip (motion blur), zoom punch, glitch, speed ramp, plus FFmpeg `xfade` set.
- **Finishing FX:** grain, vignette, chromatic aberration, impact shake, procedural light leaks/flares, letterbox, highlight glow. Subtle defaults.
- **SFX:** procedural whoosh/riser/impact/sub-drop; first-class support for licensed/CC0 SFX packs placed on hit-points.
- **Not in scope:** illustration/key art, recreated platform or rating logos (use official brand-kit files), generative imagery.
- **Architecture:** each template/effect is a plugin (param schema + renderer + preview); effects are filtergraph fragments inside the deterministic render path; graphics render to alpha frame sequences composited by FFmpeg. Optional Lottie import in M7.

## Motion engine (approved: option A)

- M1 defines a `MotionRenderer` plugin interface; built-in canvas + FFmpeg renderer is the default.
- **EffectCraft** (storytold/effectcraft, MIT/Apache-2.0, alpha) as an optional adapter plugin: generate `.ecproj`, render headless via `effectcraft-cli render`, composite ProRes 4444 alpha with FFmpeg. Pinned version, contract tests, fallback to built-in renderer. Lottie as stable interchange. "Open in EffectCraft" for hero-shot polish.
- 1–2 day spike before M5 (headless Linux, alpha output, determinism, speed) decides go/no-go.
- After Effects `.jsx` export kept as a separate handoff option.

## Game repo knowledge (local)

Point a project at a local game repository; TrailerForge extracts a **Game Knowledge digest** that feeds brief auto-fill, storyboard generation and the capture pack (real level, boss, ability and item names; scene-based capture grouping; setup hints such as debug commands or save files).

- **Read-only and local:** never writes to the game repo; respects `.gitignore`, user include/exclude globs, size caps; skips binaries and LFS pointers; secret files (`.env`, keys, credentials) are always excluded. Incremental re-scan by file hash.
- **What leaves the machine:** only the digest (names + short descriptions), never source code. The digest is shown in a review panel with per-entry toggles before any LLM call; Chat Handoff and Ollama keep it fully local.
- **Extractor plugins** (`KnowledgeExtractor` interface; **priority: generic + Unity**, the user's engine): generic (README, design docs, localization CSV/PO/JSON, achievements, store text), Unity (product name, build scenes, ScriptableObjects, prefab names), Godot (`project.godot`, `.tscn`, `.tres`), Unreal (`.uproject`, `DefaultGame.ini`, map/asset names from paths, exported DataTables).
- **Git-aware (optional):** "what changed since tag X" for update/DLC and feature-spotlight trailers.
- **Schema:** `project.sources[]` (path, extractor, globs, last scan, digest hash); digest entities (level, character, enemy, boss, ability, item, mechanic, quest, cutscene, achievement, music, art) with source paths and confidence; storyboard slots can reference entity ids. Digest cache lives in `cache/`; user edits to entities are saved in the project.
- **Milestones:** schema + extractor interface in M1 (with 1.3/1.7); extractors, digest review UI and brief auto-fill in M2.

## Claude Code integration

1. **Claude Code LLM provider** — `providers/claude-code` calls the locally installed `claude` CLI headlessly, using the user's own Claude Code login (no API key, no per-call billing). Output is validated against the same schemas as every provider. Default route when Claude Code is installed and no API key is set. Intended for the user's own local use; distribution would require each user's own install or an API key (check Anthropic terms before shipping). Interface in 1.9, implementation in M2.
2. **TrailerForge MCP server** — exposes typed commands as MCP tools (project/brief/storyboard read and edit, section regenerate, auto-cut, Quality Gate report, render) so Claude Code can drive projects. All edits go through the command bus, so they are validated, undoable and in version history. Core tools in M2, extended in M4–M6.
3. **Deep repo scan via Claude Code (opt-in)** — Claude Code explores the game repo (ScriptableObjects, scripts) to build a richer knowledge digest: mechanics, boss phases, debug commands for capture setup. Sends repo contents to Anthropic, so it is off by default with an explicit warning; results go through the same digest review panel. M2.

Estimated cost: ~50–80k extra output tokens (~+3–5% overall).

## General video editing extensibility (design for, don't build)

- Core is domain-neutral; game-trailer specifics (video types, HUD detection, gameplay labeling, platform badges, capture tips) live in a **Game Trailer domain pack** plugin.
- Timeline schema is a general multi-track model (video/audio/graphics tracks, nested sequences, keyframes on any property); storyboard slots are a layer on top of it, not the timeline itself.
- Media layer handles camera/phone footage: rotation metadata, VFR, HDR/log, mixed fps, multi-channel audio, audio-based multicam sync (later).
- Future "General Editing pack": full NLE tools (ripple/roll/slip/slide, multicam, color, audio mixer).

## Milestone 3 — Capture Pack

Turns an approved storyboard into everything needed to **record the footage**: a checklist grouped by where and how to record, recording settings, per-shot tips, and a printable/shareable pack. Footage ingest and matching are M4; here the user only marks shots as recorded by hand. Principles: deterministic first (grouping, ordering, durations, settings), LLM only for optional tips; local-only; derived data is never stored as a second source of truth (the pack is computed from `project.json`, only user edits such as status and notes are stored through commands); lives in the Game Trailer pack and `engine`, shown in `apps/ui`.

Design decisions (all four defaults confirmed by the user 2026-10-24): pack formats [Markdown + printable HTML; PDF only via browser print], recording-settings source [brief platforms + a small table in the pack, editable], whether capture notes live on the slot [yes, `extensions['game-trailer'].capture`], grouping key [`location`, then `setup`, then entity].

## Milestone 4 — Ingest + auto-cut

Turns recorded footage into a **first rough cut on the music**: find the recordings, match each to its storyboard shot, analyse footage and music locally, and assemble an editable timeline with a reason on every cut. Principles: deterministic and local by default (matching, take choice and the cut give the same result for the same input); footage and frames never leave the machine; files are referenced where they are, never copied unless the user asks; `project.json` stores only user decisions (attached clips, chosen takes, trims, beat-grid nudges, the timeline) while probe data, proxies, analysis and vision embeddings are regenerable cache keyed by content hash; every edit is a typed, undoable command; timeline time is integer flicks. J/L cuts, screen-direction continuity, speed ramps and the full Quality Gate pass come in M6.

Design decisions (confirmed by the user 2026-10-24): finding files [import by hand (browse files or folders) **and** drag and drop **and** an optional watched folder such as the OBS output folder]; matching [shot code printed in the capture pack and typed into the file name matches automatically; other files get ranked suggestions from recording order, length and **local AI vision** (CLIP-style model run on the user's machine, opt-in one-time model download through `Egress`), confirmed by the user]; first auto-cut [rough cut on the music: one take per shot, cuts snapped to beats and bars, in/out points from local analysis, hit points honoured, missing shots as placeholders]; AI in the cut [deterministic cut, plus an **optional LLM take ranking** from text only: notes, durations, analysis numbers and redacted shot text; never frames or footage].

## Milestone 6 — Review + render

Turns every version into **finished files**: one deterministic render compiler (timeline → one FFmpeg filtergraph for picture, reframe crops and blurred fill, transitions, effects, graphics overlays, and an audio mix with ducks and loudness), crash-safe resumable render jobs, the full **Quality Gate** before an export, review screens with timestamped comments and approval per version, platform export presets, and **NLE handoff** (FCPXML, OpenTimelineIO, EDL). Also the edit-grammar pieces M4 left for here (J/L cuts, screen-direction continuity, speed ramps) and the M5 gaps (re-snap shortened versions, transitions next to a card, flash checks for plugin transitions, brand fonts and logo in the browser preview). Principles carried over: `project.json` stores only user decisions (export settings, comments, approvals, J/L offsets); version timelines, render plans, segments and frames are derived, keyed by content hash and never stored twice; every edit is a typed, undoable command; time in integer flicks; same project + same inputs = same render plan, and the same output bytes with the same FFmpeg build and a software encoder; nothing leaves the machine (uploading to platforms is not M6 work).

Determinism, where it holds and where not: the render plan (filtergraph, inputs, encoder arguments) and its hash are pure functions of the project, the derived timeline, cached analysis and the installed plugin set. Output bytes are identical for the same plan, the same FFmpeg build and a software encoder run with fixed threads and `-bitexact` flags (libx264, libx265, ProRes `prores_ks`, PCM/AAC with pinned settings); the render manifest records the FFmpeg version and build string, and a different build is reported as "plan identical, bytes may differ". Hardware encoders (NVENC, QSV, AMF, VideoToolbox, VAAPI) are not bit-identical across drivers or GPUs: they are allowed for drafts only, marked as such in the manifest.

**Confirmed 2026-10-28:** all eight defaults as proposed (five presets with software encoding for finals and hardware for drafts; drafts, comments and approval stamped with the plan hash; the three-tier Quality Gate; FCPXML → OTIO → EDL; re-snap shortened versions; the M5 gaps as listed, desktop bundling in M7; clip audio off by default with J/L offsets, screen direction as a warning, frame-blended ramps).

Design defaults (proposed 2026-10-28, all confirmed the same day):

1. **Export presets per platform:** _YouTube_ (16:9, source resolution up to 4K, H.264 High CRF 16, AAC 320k, −14 LUFS, −1 dBTP), _Steam_ (16:9 1920×1080, H.264 High at ~12 Mbit/s, AAC 192k; Steam's store player re-encodes, −14 LUFS), _Vertical social_ (9:16 1080×1920 for Shorts/Reels/TikTok, H.264 High CRF 18, AAC 256k, −14 LUFS), _X/Twitter_ (16:9 or 1:1, H.264 High ≤ 25 Mbit/s, −14 LUFS), and a _Master_ (ProRes 422 HQ 10-bit .mov, PCM 24-bit, −16 LUFS) for archiving and editors. The first export of a version picks the preset matching its format target; settings per version are stored as user choices. Alternative: Master only, the user transcodes.
2. **Hardware encoding:** final exports use the software encoder (bit-identical, see above); hardware encoders when detected for review drafts only, with a setting to allow them for finals too (manifest says not reproducible). Alternative: hardware whenever detected.
3. **Review and approval:** per version a review draft (720p, fast preset, cached by plan hash) in an in-app player; timestamped comments anchored to a time and, when there is one, the timeline item (resolve/reopen, stored in `project.json`); **Approve** stamps the version with its render plan hash, and any later change to the plan marks the approval stale. 4. **Which Quality Gate checks block an export:** _blocking_ (no override): photosensitive flash risk measured on the rendered picture (WCAG 2.3.1, ≤ 3 general/red flashes a second), true peak above −1 dBTP after the limiter, digital clipping, placeholders or missing media left in the cut, output resolution/frame rate/duration off the preset; _blocking with an override_ (one click, reason written to the decision log): integrated loudness off target by more than 1 LU, black or flash frames inside the picture, text outside title-safe, A/V sync drift over half a frame; _warnings_: jump cuts, text read time, pacing curve, screen-direction flips, shortened-version cuts off the beat, brand contrast. Alternative: everything a warning.

## Milestone 7 — Polish

Makes TrailerForge something a person can install on Windows and use from a new project to an exported trailer without the terminal: faster renders, the missing finishing pieces (clip transforms in the render, drag-to-edit on the Cut timeline, which the user asked for "once the tool is complete"), the LLM path brought under the Egress rule (and a local model option), an opt-in AI critique, a first-run health check, a demo project, the desktop installer, and a usability and accessibility pass over every tab. Principles carried over: `project.json` holds only user decisions; every edit (including every drag) is one typed, undoable command in integer flicks, with a keyboard path kept; renders stay deterministic (faster must not change a byte); nothing leaves the machine outside `Egress`, and anything sent to an LLM is text only, with excluded entities removed and ids limited to the installed set. Not M7: platform uploads, built-in recording/OBS, automatic Unity recording, the deeper offline repo scan, Lottie import, reference-trailer import (all stay in "Potential extensions" or later milestones).

Design decisions (recommended defaults):

1. **Render speed.** Render segments in parallel (workers = cores ÷ 2, each FFmpeg with fixed threads, so the bytes do not depend on how many run at once), decode each source once per segment instead of once per item, cache the measured loudness by audio plan hash, and run the output gate's picture decode at the same time as the poster. Target: at least 1× real time for a 1080p YouTube export on an 8-core CPU, checked by the timing test; same bytes as today's serial render. Alternative: hardware encoders for finals (refused: not reproducible).
2. **Drag-to-edit on the Cut timeline** (in M7, as requested). Drag a clip along its track or to another track of the same kind, drag either edge to trim; snapping to beat cut points (one frame ahead of the beat), bars, section markers and neighbouring cuts, with a modifier to turn snapping off; **overwrite** by default (refused where it would overlap, with the reason shown), **ripple** with a modifier (later items on that track move with it); a live ghost and time readout while dragging; one undoable command per drop (`core/timeline.move` and `trim` extended with a target track and ripple); keyboard: select, then arrow keys move by a frame and with Shift by a beat. Alternative: ripple by default.
3. **LLM calls through Egress.** Extend `Egress` with an `llm` channel: POST to an allow-listed host only (the provider's API host, or `localhost` for a local model), the prompt's size and purpose logged (never its text), the same exclusion guard checked again at the boundary, and providers can no longer open connections on their own (a test fails if one does). Add an **Ollama** provider (local model, `localhost` only) so storyboard, tips and critique can run fully offline; OpenAI stays unbuilt until asked. Alternative: Egress only, no new provider.
4. **AI critique** (opt-in, route `critique.run`, Opus/high). Sends the brief, the storyboard and measured cut facts (shot lengths, cut-on-beat share, pacing curve, Quality Gate findings) as text only, with the same exclusion redaction and leak guard as take ranking; no frames, paths or file names. It returns at most ten notes, each tied to a slot or a moment, with an optional fix that is a typed command payload the user can apply or dismiss (never applied automatically); notes are stored on the review as comments by "critique", and a cancel stores nothing. Alternative: defer critique past M7.
5. **Desktop packaging.** Windows x64 first, unsigned NSIS installer from `electron-builder`, bundling `assets/` (fonts), resvg's win32 binary and the analysis sidecar's source with a pinned `uv`; FFmpeg is **not** bundled (plan decision 5: the user's own install, detected at start with a guide); the sidecar's Python environment is created by `uv` on first run after the user agrees (the first-run check shows the size; packages come from PyPI through uv, which is logged as a setup step, not app traffic). macOS/Linux packages and code signing later. Desktop polish: no "Disconnect" button and no default File/Edit/View menu in the desktop app, Windows-style path placeholders.
6. **First run and health.** A Setup screen that checks FFmpeg/ffprobe (version, required filters and encoders), the sidecar (uv, Python, packages), free disk space, the vision model (optional), the LLM routes (key present or Chat Handoff), and hardware encoders, each with a plain fix; rerunnable from Settings; the service refuses renders when FFmpeg lacks a filter the plan needs, with that filter named.
7. **Demo project.** "Try a demo" builds a project from locally generated footage (labelled synthetic gameplay shots with movement and no flashing) and generated music with a known beat (plan decision 7), already matched and cut, so every tab has something to show; nothing downloaded.
8. **Clip transforms in the render.** Position, scale and opacity keyframes on clips (no rotation) (already in the schema, warned as "not rendered" today) are compiled with the same evaluator as the preview; the Cut preview draws them too; NLE handoff writes them as markers as before.

## Milestone 8 — EffectCraft motion plugin

Adds EffectCraft (storytold/effectcraft, MIT/Apache-2.0, alpha) as an **optional** `MotionRenderer` plugin for hero-shot motion graphics, as approved in "Motion engine (option A)". **The main reason for the integration (user, 2026-10-29): an LLM (Claude through the engine, or Claude Code through MCP) writes custom effects as EffectCraft projects from a plain-words request.** A small set of ready-made templates is kept beside it (user, same day). The built-in SVG/resvg renderer stays the default and the fallback; nothing in M1–M7 depends on EffectCraft. Moved ahead of the Planner (now M9) at the user's request, 2026-10-29. The M5 decision to skip the spike is reversed here: the spike is task 8.1 and decides go/no-go.

Design decisions (recommended defaults, **to confirm**):

1. **Spike first (8.1).** Headless Linux and Windows, ProRes 4444 alpha output, determinism (same bytes twice), speed, licence of the pinned version and its dependencies, and whether the CLI needs a GPU or window. No-go ends the milestone after 8.1 with a written finding; the interface and fallback stay.
2. **Optional and pinned.** The user installs EffectCraft themselves (like FFmpeg); Setup detects its path and version, accepts only the pinned version range, and shows a plain fix. Nothing is bundled or downloaded by the app. Alternative: bundle it (refused until the licence check in 8.1).
3. **Adapter shape.** `MotionRenderer` plugin `effectcraft`: generates an `.ecproj` from a Scene or template params (brand tokens included), renders headless with `effectcraft-cli render` into a scratch dir, returns a ProRes 4444 clip. The compiler uses it like the handoff alpha clips, as a graphics-track input; content-hashed so unchanged scenes render once.
4. **Which templates (kept).** A small set of EffectCraft-backed templates (`effectcraft/title-reveal`, `logo-sting`, `kinetic-text`) next to the built-in ones; the picker marks them "needs EffectCraft". Without it they are hidden and a storyboard that uses one falls back to the nearest built-in template with a warning.
5. **Determinism.** The plan hash includes the EffectCraft version and the `.ecproj` hash; a non-reproducible result is flagged `reproducible: false` in the render manifest (as hardware encoders are) and a warning shows at export. Approvals still vouch for the plan hash.
6. **Privacy.** Local process only, no network, run through the same sandboxed-spawn rules as FFmpeg; the Egress log stays empty (spied in tests).
7. **README check (2026-10-29, before the spike).** The EffectCraft README (reachable at raw.githubusercontent.com even though github.com is blocked here) says: pure Rust, MIT OR Apache-2.0, no FFmpeg; projects are readable versioned JSON (`.ecproj`); `effectcraft-cli render --comp <name> --out <file>` renders headless, ProRes MOV up to 4444 XQ with alpha and WebM VP9 with alpha are supported; every action is a command reachable from the CLI (`exec <command> '<json>'`), a JSON control channel and an MCP server (`effectcraft-cli mcp`); Lottie import and export. Status: alpha, first commit 1 October 2026, about 45% of the way to full production use by its own estimate, macOS best tested, Windows and Linux have known interaction bugs. This supports the LLM-authoring idea and the adapter shape; it does not settle determinism, speed, the exact `.ecproj` schema or how stable it is between versions, which the spike must measure.
8. **Custom effects written by an LLM (the headline feature).** New route `effectcraft.author` (Opus/medium) and MCP tool `effectcraft_author`: the request (words, duration, beat or hit point to land on, brand tokens) goes out as text only; the reply is an EffectCraft project that is parsed against the format (strict schema built from the spike's findings), size and length limited, then previewed as a still or short clip. Rejected output gets one repair round with the validator's errors. Exclusion redaction and leak guard as for take ranking; a decision record explains the request. Conditional on the spike: if the format is not a documented text format, this is dropped and the templates carry the milestone.
9. **Interchange and polish.** "Open in EffectCraft" exports the `.ecproj` for hand polish and imports the rendered clip back as a replaced graphic (one undoable command). Lottie and After Effects `.jsx` stay out.

## Milestone 9 — Planner scaffold

Opens the door for the Content Calendar Planner without building it: the project already carries `campaignId`, `scheduledDate`, `platformTargets[]` and `status` (M1), assets carry `themes` and `reuseHistory`, and the plugin API has the `nav.planner` slot. M9 makes those fields usable (set them, query them, see them on a calendar behind a feature flag) and adds the stable `core.projects.createFromCalendarSlot(slot)` API a future Planner plugin calls. It is a scaffold: no social posting, no analytics, no scheduling automation, no network. Principles carried over: `project.json` holds only user decisions; every change is a typed, undoable command; local-first; the Planner is a plugin-shaped module behind `features.planner`, off by default.

Design decisions (recommended defaults, **to confirm**):

1. **Where campaigns live.** A campaign (id, name, goal, start/end date, platform targets, notes) is app-level data in `<home>/planner/campaigns.json` (like the asset library), because one campaign spans projects. Projects point to it by `campaignId`; a dangling id is a warning, never a load failure. Alternative: a campaign as a project (refused: nothing to cut).
2. **Calendar slots.** A `CalendarSlot` is `{ id, campaignId?, date, platformTargets[], videoTypeId?, title, notes? }`, stored beside campaigns. `createFromCalendarSlot(slot)` makes a project with the schedule fields and brief title filled in, status `idea`, and remembers the slot id in `extensions.core.calendarSlotId`. Same input gives the same project fields (id and clock injected).
3. **Scheduling commands.** New `core/project.set-schedule` (`scheduledDate`, `campaignId`, `platformTargets`; each nullable/optional; one undo step); the existing `core/project.set-status` stays the one status path. Dates are plain `YYYY-MM-DD` in the user's local calendar, no time zones.
4. **Footage reuse.** Attaching a take to a shot records a `reuseHistory` entry on the library asset (`projectId`, `slotId`, `usedAt`); detaching removes it. Project deletion is not tracked (history may name a gone project; shown as "removed project"). `core/assets.set-themes` edits themes. A query lists assets by theme and by "unused in this campaign". Nothing is suggested automatically.
5. **Feature flag.** `features.planner` (Settings toggle, default off) shows the Planner tab through the `nav.planner` slot; with it off, no Planner code loads and nothing changes anywhere else.
6. **Scaffold UI.** A month/list view of scheduled projects by campaign and status, "New from this day" (calls `createFromCalendarSlot`), drag a project card to another day (one `core/project.set-schedule`), and a campaign editor. Read-mostly: no publishing, no reminders. Keyboard path for every action (move to date field).
7. **Surfaces.** Engine ops, service routes, CLI `tforge planner ...`, MCP read tools plus the command tools; the Planner reads project summaries from the projects list without opening each one.

## Potential extensions (not scheduled, not in any milestone)

Ideas recorded so they are not lost. None of these is planned work; do not build them or design around them without the user asking.

- **Built-in recording / OBS control** (parked 2026-10-23): a plugin that drives a recorder (for example OBS over its WebSocket API) so a capture checklist item can start, stop and name a recording, and the file attaches to its slot. Today "capture" means the checklist only (M3); the user records in their own tool and M4 imports the files. If ever built, it must stay local-only, be opt-in, and use the same plugin API and typed commands as everything else.
- **Seamless drag-and-drop timeline editing** (requested 2026-10-24, after the tool has full functionality, e.g. M7 polish): drag shots along and between tracks on the Cut timeline, with snapping to beats, bars and neighbouring cuts, live preview while dragging, and ripple or overwrite behaviour. M4's Cut UI (4.13) uses buttons and keyboard trims only. Every drag must still land as one typed, undoable `core/timeline.*` command, in integer flicks, with a keyboard path kept for accessibility.
- **Deeper offline repo scan** (requested 2026-10-25, a future extension): get closer to the Claude Code deep scan without sending code off the computer, as a mix of (a) a **local model** provider (for example Ollama on the user's NVIDIA GPU) with a local deep scan that reads the repo in chunks and builds the same knowledge entities, exclusions airtight since nothing leaves the machine, quality below Claude and slower; and (b) **smarter Unity rules**: enemy/boss/ability classes from C# base classes and `[CreateAssetMenu]` types, enum lists (`EnemyType`), Animator states, Input System actions, on-screen UI text, Addressables groups. Roughly 3 Opus tasks. Until then: deep scan once, then offline rescans (they never mark deep-scan findings stale).
- **Automatic recording from Unity** (requested 2026-10-25, a future extension; Unity only, other engines keep the parked OBS idea): a Unity Editor package ("TrailerForge Capture") that works through files only: it reads the exported `capture-pack.json` and writes recordings named with their shot codes to a watched folder, which TrailerForge imports and matches by code. Recording uses Unity Recorder (resolution and frame rate from the recording settings, lossless or high bitrate, optional fixed-timestep capture for smooth footage, a HUD-free camera or layer). Levels of automation: (1) one-click record per shot (settings, naming, length, tick-off); (2) automatic set-up through the game's debug commands or hooks (load save, spawn, god mode, time of day); (3) hands-free camera-only shots with Cinemachine/Timeline; (4) **play once, film many times, the first to build**: record the scene's motion while the user plays, then re-render it from other cameras, HUD on and off, slow motion, 4K at a locked frame rate (particles, some physics and shader effects need extra handling); (5) scripted shots written by TrailerForge from the storyboard against a "trailer mode" API the game exposes (spawn, teleport, set state, AI-driven player), rendered overnight with several takes; (6) an AI agent playing the game, realistic only for slow games such as city builders. AI-driven play looks robotic, so it suits wide and background shots more than skilled-play hero moments; levels 2 and 5 need work in the game project itself. A live link (shots ticking off in the app while recording) could come later over the app's local connection.
